# 已审核候选的显式发布交接

调度 Agent 仍由外部 MCP 调用方承担。Relay 应用层保留开发、宿主测试、审查和精确候选发布的职责，队列内核不解释这些阶段，也不增加通用流程引擎。

## 适用范围

当工作流以 `publish:false` 成功结束、最后一轮候选已有成功宿主测试和 `approved` 审查，并且尚未尝试发布时，可以通过任务页面、`POST /api/tasks/<id>/publish-approved` 或 MCP `relay_publish_approved` 显式交接给发布器。

这是新的不可变后继任务，不是失败重试。原任务、测试、审查和候选 SHA 不被覆盖；不会重新调用开发 Agent、测试命令或审查 Agent。已有的 `publish:true` 一体化工作流继续适用。

后继结果为展示复用原阶段证据，并明确标注来源；新增发布输出可能触发既有 16 KiB 结果显示摘要限制。原前置结果保持不变，交接 payload 另存原结果的精确字节及摘要，不把截短后的显示内容当作完整审核证据。

页面先展示候选、GitHub 仓库、基础分支及发布适配器，调用者明确确认发布并接受原宿主测试。原测试只证明当时执行的结果；Relay 没有冻结任意测试命令读取的全部外部输入，因此这一步不表示重新验证或自动缓存命中。发布结果及 GitHub 示例 PR 正文保留这一来源说明。需要新测试或新审查时，不应选择接受旧证据的交接动作。

## 一次交接的约束

- 请求中的候选和目标来自服务端操作预览；不允许请求指定任意命令、路径或发布目的地
- 接纳时冻结前置结果摘要、精确候选、目标及发布配置绑定；排队后发生漂移，执行前明确拒绝
- 同一前置任务只有一个后继预留；重复请求复用既有操作，不会创建第二个发布任务
- 宿主复用同一固定工作区及独占所有权，发布前仍检查候选字节、索引、干净状态及原审核证据
- 发布默认仍是 dry-run；真正推送取决于宿主已经允许的发布配置。真实发布只创建 draft PR，本地成功不代表 CI 通过、可合并或已合并

原来的 `publish:false` 并未授权发布。新的动作明确接纳页面当时展示的宿主发布配置，不声称旧审查已经授权同一个发布器；已有成功任务仍需通过原开发、测试和审核工作区绑定检查。程序身份核对是宿主文件元数据核对，不是整个运行环境的可复现构建证明；解释器参数指向的脚本、依赖和外部服务仍属于可信宿主管理范围。

## 工作区与有效期

交接请求前，成功工作区仍遵守原有可选成功 TTL；如果现场已被清理，历史成功记录不能代替发布所需的候选字节。

已接纳的交接有固定 24 小时授权期限，重复请求不会延长期限。尚未执行的预留或排队交接在期限内保护成功前置工作区；到期或取消排队交接后，此项保护解除，原有成功 TTL 可以重新适用。保留预览说明保护原因及有效期，不将所有成功工作区永久保留，也不增加删除接口。

已经领取执行或进程状态未知时，期限不会被用来推断进程结束。仍需遵守现有宿主所有权、进程回收与人工核对规则；失败/未知现场仍按既有策略保留。

## 中断与不确定副作用

发布前写入持久尝试标记。网络中断、返回值不完整或副作用成功后落库失败，可能产生“已经推送但未记录成功”的情况；Relay 不宣称外部效果恰好一次，也不会盲目重放 push 或 PR 创建。

出现发布核对提示时，应由可信操作员核对固定目标、分支和候选 SHA，以及是否已有 PR，再决定后续处理。更换幂等键、普通 retry 或重跑开发都不能绕过发布尝试标记。原任务历史始终保留。

独立的确定性 CI 跟踪和按目标授权合并属于后续交付范围；此交接本身不轮询模型，不等待远端 CI，也不自动转为可合并 PR。
